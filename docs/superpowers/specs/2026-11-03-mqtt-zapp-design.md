# mqtt-zapp — Design

Date: 2026-11-03
Status: draft, awaiting approval (builder-check questions resolved)

## 1. Intent

mqtt-zapp is a Rust MQTT client for exploring a broker. It aims for feature
parity with [MQTT Explorer](https://github.com/thomasnordquist/MQTT-Explorer)
and adds a **terminal UI (TUI)** that works over SSH and in a local terminal.

### Why

- The user's daily loop with MQTT Explorer is: **find a device**, look at it in
  the **topic tree**, **watch its messages arrive**, and **publish** to test how it
  reacts.
- They need to do that over SSH, on boxes that have no display.
- MQTT Explorer's search is frustrating. Typing `wzr` does not find `wzr`.
  The user has to type `device:wzr`-style syntax instead.
- MQTT Explorer is not regularly maintained, with few bug fixes and few new
  features. mqtt-zapp should be easy to keep current.

### Success looks like

The user SSHes into a box, runs `mqtt-zapp`, and picks a saved broker.
They type `/` followed by part of a device id, and the tree narrows
instantly. They select the device's topic, watch its JSON messages update
live with a diff against the previous value, and publish a test command
without leaving the TUI.

## 2. Reference environment (observed 2026-11-03)

This is the user's broker at `192.168.22.5`. It was sampled anonymously and
read-only for about 12 seconds.

- Mosquitto 2.0.21 on plain `1883`. No other common ports were open:
  8883, 9001, 8080 and 8081 were all closed.
- 41 clients were connected, sending about 470 messages a minute.
  The broker holds 226 retained messages, and about 240 distinct topics
  appeared in 12 seconds. **Scale is hundreds to low thousands of topics,
  not hundreds of thousands.**
- Topic families:
  - `tasmota/{tele,stat,discovery}/tasmota_<ID>/{SENSOR,STATE,RESULT,LWT,MARGINS}`
  - `muh/{esp,sensors,lights,pc,berry,portal}/…` (the user's own devices)
  - `shellies/…`
- Payloads come in three forms:
  - compact JSON, up to about 1 KB
  - plain strings (`online`, IPs, version strings)
  - **pretty-printed multi-line JSON** (an APC UPS status)

  Some payloads contain no JSON at all.

Other brokers the user connects to use **username/password and TLS**, and
sometimes **WebSockets**. The user works with "a few" brokers. The user
confirmed that the other brokers are about the same size as this one.

## 3. Goals

### Phase 1 — TUI essentials (this design's build target)

The user decided that Phase 1 is **the essentials**: every item marked
**[core]** in §4. The success scenario in §1 depends on two features that
are now promoted to [core]: the startup connection picker, and the diff
against the previous message. Phase 1 is done when all [core] items work in
the TUI against the reference broker, the tests in §6 pass, and CI produces
a release binary.

### Phase 1.x — remaining parity (later TUI releases)

Every unmarked item in §4 ships in follow-up releases. Any MQTT Explorer
features the builder finds missing from §4 also go here, not into Phase 1.
These include charts, Sparkplug B, `$SYS` stats, clearing retained topics,
sorting options, and MQTT 5.

### Phase 2 — Desktop GUI (later, separate design)

This phase adds a desktop GUI that reaches feature parity on top of the
same core. The Phase 1 architecture must make this possible without a
rewrite (see §6). It is not built in Phase 1.

## 4. Feature list (parity target)

The MQTT Explorer list is drawn from the builder's knowledge of the app.
The builder should check it against the upstream README and app before
planning, and add anything missed. **[core]** marks a feature the user
explicitly named. Phase 1 must ship all [core] items. The other items are
parity and may be sequenced after the core.

### 4.1 Connections
- [core] Saved connection profiles:
  - name, host, port
  - protocol `mqtt` / `mqtts` / `ws` / `wss`, plus the WebSocket path
  - client id (auto-generated by default)
  - username/password
- [core] TLS settings:
  - CA certificate
  - optional client certificate and key
  - "allow insecure / skip verification" toggle
- Per-profile subscriptions. The default is `#` and `$SYS/#`, and the user
  can edit the list.
- MQTT protocol version 3.1.1 and 5.
- [core] Auto-reconnect, with the connection state visible in the UI.
- [core] Connection picker at startup, plus `--profile <name>` on the command line.
  Ad-hoc `--host/--port/--user/--tls` flags allow connecting without a
  profile.
- Passwords are never stored in plaintext in the profile file. They go in
  the system keyring when one is available. Otherwise, mqtt-zapp prompts at
  connect time, which is the normal case on headless SSH boxes.

### 4.2 Topic tree
- [core] A live hierarchical tree built from the `/` levels of each topic.
  Every node shows:
  - its last value, previewed and truncated
  - the message count for the subtree
  - the number of child topics
- [core] New topics appear as they arrive. A node visibly flashes or
  highlights when it receives a message.
- Retained messages are marked.
- Expand and collapse a node, or a whole subtree.
- Sort options: by name (natural sort, so `tasmota_2` comes before
  `tasmota_10`), by message count, or by most recent.
- Delete a topic's retained message, and recursively clear the retained
  messages in a subtree. Both need confirmation.

### 4.3 Search / filter — key differentiator
- [core] Plain text, with no prefix syntax required. `wzr` matches any
  topic whose **full path** or **latest payload** contains `wzr`,
  case-insensitive.
- [core] The filter is live and updates on every keystroke. Newly arriving
  messages that match appear without re-running the search.
- [core] The filtered tree keeps the ancestors of every match, so you can
  see where each match sits, and auto-expands down to the matches.
- Match highlighting in the topic path and payload preview.
- Optional extras that are always opt-in and never required: multiple
  space-separated terms (AND), and a regex mode.
- Search must stay responsive with thousands of topics and payloads around
  1 KB.

### 4.4 Message view (selected topic)
- [core] The latest value, updated live, with metadata:
  - timestamp
  - QoS
  - retained flag
  - payload size
- [core] Payload formatting:
  - Auto-detect JSON and pretty-print it with syntax colouring.
  - Already pretty-printed or multi-line payloads must display correctly.
  - Fall back to raw text.
  - Hex view for binary payloads.
- [core] Message history for the topic, using a bounded ring buffer per
  topic. The user can browse the history list and open any past message.
- [core] Diff between the current message and the previous one. Diffing
  any two history entries is Phase 1.x. For JSON, show added, removed and changed keys.
- Copy the topic path or the payload to the clipboard. Over SSH this uses
  OSC 52.
- Sparkplug B decoding (protobuf) for `spBv1.0/…` topics.

### 4.5 Charts
- Plot numeric values over time for a topic, using its plain numeric payload.
- Plot a numeric field inside a JSON payload, chosen by path, for example
  `ENERGY.Power` in a Tasmota SENSOR message.
- Multiple series can be shown in the TUI as braille or line charts.

### 4.6 Publish
- [core] Publish to a topic. By default, the topic is pre-filled from the
  selected tree node and can be edited.
- [core] Payload editor:
  - multi-line
  - JSON format/validate helper
  - QoS 0/1/2
  - retain flag
- Payload history: recently published messages can be recalled per topic.
- Optionally, open the payload in `$EDITOR` (nvim) and read it back.

### 4.7 Broker statistics
- A view of the `$SYS/#` stats: version, connected clients, message rates,
  retained count.

### 4.8 Settings
- Persisted settings:
  - history depth
  - sort order
  - auto-expand behaviour
  - timestamp format
  - theme (dark/light)

## 5. Non-goals and anti-goals

### Non-goals (Phase 1)
- The desktop GUI. It has its own design later.
- A broker or server mode. mqtt-zapp is a client only.
- Persisting received messages across restarts. History lives in memory
  for the session.
- Scripting or automation.

### Anti-goals (a failure even if it technically works)
- Search that needs special syntax to find a plain substring.
- A TUI that stutters, or drops input, under hundreds of messages a minute.
- Multi-line or pretty-printed payloads rendered as one mangled line.
- Requiring a GUI, X11/Wayland, or a running keyring daemon to work over SSH.
- Plaintext passwords in config files.
- A codebase that is hard to change, which would repeat the maintenance
  problem the user has with MQTT Explorer.

## 6. Decisions

### Decided by the user
- The language is Rust and the name is `mqtt-zapp`.
- The TUI comes first and the GUI follows later.
- The TUI must work over SSH and in a local terminal.
- Search matches topic names **and** payloads using plain text.

### Claude's calls (the user can override any of these)
- **Core/UI split.** One Cargo workspace:
  - `mqtt-zapp-core` holds the connection handling, the topic tree, history,
    search, the profile and config store, and the payload decoders. It
    contains no UI code.
  - The `mqtt-zapp` binary holds the TUI front end.
  - A future GUI crate reuses the core.

  The core exposes state and events that are agnostic to any particular UI.
  The kind of GUI for Phase 2 is still undecided. It could be a native Rust
  GUI or a webview such as Tauri. As a hedge, the core's public events and
  state snapshots derive `serde::Serialize`, so either kind could use them.
- **Stack.**
  - `tokio`
  - `rumqttc`, which covers MQTT 3.1.1 and 5, TLS through rustls, and
    WebSockets
  - `ratatui` + `crossterm` for the TUI
  - `serde` / `serde_json`
  - `clap` for the command line
  - `keyring` for passwords, falling back to a prompt
  - `toml` for config files

  The builder may swap any crate that turns out unsuitable, but must say
  why.
- **Config location.** XDG paths: `~/.config/mqtt-zapp/{profiles.toml,settings.toml}`.
- **Key bindings.** The TUI is vim-style:
  - `j/k` move, `h/l` collapse and expand
  - `/` search, `p` publish
  - `y` yank (copy) the topic or payload
  - `d` delete retained, `q` quit, `?` help

  The user uses nvim. These defaults are a guess and have not been
  confirmed. Because of that, the keymap is **remappable** through
  `settings.toml` from the start.
- **Distribution.** A single static binary, `x86_64-unknown-linux-musl`, so
  it can be copied to SSH hosts with `scp`. The user confirmed **x86_64
  only**, so there is no ARM cross-compilation. Use rustls with the `ring`
  backend, and make sure the keyring backend doesn't force a dynamic
  libdbus link. If it does, put keyring support behind a cargo feature that
  is off in the musl build, and prompt for the password instead.
- **Hosting/CI.** The repo is on GitHub (`github.com/13/mqtt-zapp`, branch
  `main`) and uses GitHub Actions. Integration tests run Mosquitto as a
  service container. Tagged pushes build the release binaries.
- **Maintainability.** The core has unit tests: tree insertion, the search
  semantics in §4.3, the JSON diff, and the history ring. There are
  integration tests against a throwaway Mosquitto instance. CI runs
  `cargo fmt` and `cargo clippy` on every push.
- **Visual identity.** No visual reference to MQTT Explorer's branding or
  art. Only the feature set is matched.

## 7. Left to the builder
- The exact TUI layout. A reasonable default:
  - a tree pane on the left
  - a value/history/diff pane on the right
  - publish as a bottom panel or overlay
  - a status bar showing the connection state and message rate
- History depth defaults, and memory caps per topic and in total.
- The search implementation: an incremental index or a scan over the tree.
  Either is acceptable if it meets the responsiveness anti-goal at the scale
  in §2.
- The order in which the non-core parity features are sequenced.
- Chart rendering details.
